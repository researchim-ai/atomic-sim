# Сохраняемые параллельные EOS-кампании

Новый пакет `atomic_model_rollouts` выполняет матрицу сценариев, встроенных политик и явно заданных seed отдельными Linux-процессами. Поддержаны синхронный вызов и фоновый контроллер, пауза, отмена, общий срок, продолжение по ожидаемому SHA текущего состояния и восстановление после потери контроллера.

## Запуск

```bash
python -m atomic_model_rollouts create examples/eos_workspace/project.json --output artifacts/my-rollouts
python -m atomic_model_rollouts run artifacts/my-rollouts
python -m atomic_model_rollouts report artifacts/my-rollouts
python -m examples.eos_rollout_workflow --output artifacts/my-rollout-proof
```

`inspect` возвращает текущий SHA. Для `resume` и `recover` обязателен `--expected-sha256`. Команды `pause` и `cancel` адресуются активному поколению контроллера. Продолжение не пересоздаёт принятые физические шаги. Лимит попыток учитывает также плановое разбиение на части: его необходимо согласовать с горизонтом и `decision_slice`.

## Реализованные гарантии

- Проект, исходный код, сетка seed и бюджеты фиксируются до запуска; до 64 заданий, 8 воркеров и 4096 ревизий метаданных.
- Каждый воркер закреплён за одним разрешённым CPU; число процессов ограничено CPU-бюджетом и резервированием памяти. Число потоков основных BLAS-библиотек задаётся равным одному.
- Задание публикует native checkpoint после принятого решения. Перед запуском очередной части и после завершения процесса история воспроизводится численным ядром.
- Публикация владения процессом предшествует разрешению работы `GO`. Linux parent-death signal завершает воркер при потере породившего его потока.
- Восстановление проверяет boot ID, PID, TID и время старта. Живой либо неизвестный владелец блокировки запрещает восстановление; чужие блокировки не удаляются.
- Ошибка одного задания сохраняется отдельно. Метрики неполного горизонта не выдаются за завершённый эпизод.
- Экспорт содержит самодостаточные снимки native-состояний, исходную идентичность, SHA и пересчитываемый отчёт. Проверка заново интегрирует историю; это снимок текущего состояния, а не копия всего журнала контроллера.

## Границы

RSS измеряется периодически для основного процесса воркера; резервирование ограничивает допуск новых процессов. Это не cgroup-квота. Память и CPU контроллера и повторного аудита учитываются отдельно от бюджета воркеров. Срок останавливает диспетчеризацию и работу процессов; завершение аудита и публикация могут занять дополнительное время.

Поддерживаются доверенные встроенные политики EOS. Произвольные агентские процессы через этот интерфейс не запускаются. Seed — метаданные воспроизводимости; детерминированные модели не становятся независимыми физическими опытами при смене seed.

Сравнение с последовательными native-прогонами проверяет программную воспроизводимость. Физическая валидация установки, независимая межмашинная проверка, измеренное ускорение 2×, реальные экспериментальные данные и полное покрытие аварийного восстановления остаются отдельными задачами. Пункты AI-10.04 и AI-10.06 нельзя считать полностью принятыми только по этому прототипу.

## Аварийная квалификация — 5 ноября 2026

`tests/test_rollout_faults.py` проверяет настоящий выход отдельного процесса контроллера до и после публикации GO, остановку дочернего процесса механизмом parent-death, отказ устаревшего CAS и восстановление с завершением всех шести заданий. Неизвестное время потерянной попытки остаётся `null`.

Принудительный SIGKILL одного воркера проверяет завершение остальных пяти заданий и последующее продолжение пострадавшего. Для RSS используется явно искусственное завышенное показание наблюдателя, а не фактическое исчерпание памяти. Отдельные проверки внедряют переполнение worker.log и повреждение HEAD одного native-задания.

`validation/ai10_rollouts_installed_replay_v1.json` фиксирует прогон wheel в новой локальной venv вне checkout: 12 заданий, deadline/resume, точное совпадение native-контролей и экспорт/replay. Системные зависимости общие с хостом; независимая машина и ОС этим не проверены.

Эти проверки покрывают конкретные точки отказа. Полное перебирание аварий в каждом файловом commit, в том числе авария во время владения корневым `.lock`, остаётся открытым. Не удаляйте такую блокировку автоматически без проверки владельца.
