# AI-05: повторяемые режимы и гистерезис Radau

`HystereticRadauGraph` добавляет явный автомат режимов к проверенному
[температурному механизму событий](AI_05_STATE_EVENTS_RU.md). Переходы
активны только в текущем режиме и снова активируются при следующем входе
в него. Это даёт повторяемое управление нагревом/охлаждением без превращения
каждого цикла в новый набор одноразовых guards.

## Программа режимов

```python
request = {
    "format": "atomic-hysteretic-graph", "schema_version": 1,
    "model_input": model_input, "initial_mode": "heat",
    "minimum_residence_s": 1.0,
    "modes": [
        {"id": "heat", "commands": {"thermal_nodes": {"a": {"heat_power_w": 12500.0}}},
         "transitions": [{"id": "hot", "node": "a", "threshold_k": 310.1375,
                          "direction": 1, "to": "cool"}]},
        {"id": "cool", "commands": {"thermal_nodes": {"a": {"heat_power_w": -25000.0}}},
         "transitions": [{"id": "cold", "node": "a", "threshold_k": 310.0125,
                          "direction": -1, "to": "heat"}]},
    ],
}
model = HystereticRadauGraph(request)
result = model.advance(120.0)
```

Каждый режим объявляет команды и исходящие температурные переходы. Направление
строго +1 либо -1. Идентификаторы режимов и переходов уникальны, адресаты
существуют, весь объявленный граф структурно достижим из начального режима.
Самопереходы без сброса состояния не поддерживаются. Пустой список исходящих
переходов задаёт терминальный режим: физический расчёт в нём продолжается.
Структурная достижимость не доказывает физическую достижимость каждой ветви.

Все режимы обязаны задавать одну и ту же полную маску управляемых полей.
Например, если один режим задаёт мощность и граничное давление, второй тоже
должен явно задать оба. Активная физическая конфигурация строится из базового
входа и команд текущего режима; скрытого наследования команд предыдущего
режима нет. Остальные параметры остаются базовыми. Допустимы прежние команды
тепла, температуры подачи/окружения, давления, инжекции и напора. Топология,
роли границ, объёмы, свойства и L(T) неизменны.

Базовая модель должна быть допустимой самостоятельно. Начальный режим
применяется при создании в нулевое время, без изменения температур и энергии.
Будущие режимы проверяются физически при входе на фактических температурах,
а не при исходных холодных догадках.

## Вход, гистерезис и время режима

Все исходящие переходы при входе должны находиться строго до пересечения
в заданном направлении, с запасом 1e-7 К. Поэтому неопределённый контакт или
уже активное условие не становится неявным мгновенным каскадом. Неактивный
переход будущего режима может иметь порог, совпадающий с начальной температурой:
он проверяется лишь при входе в свой режим.

Гистерезис задаётся разными порогами в разных режимах. При возвращении в режим
его переходы активируются заново. Идентификатор может многократно встречаться
в истории; история фиксирует последовательность и исходный/целевой режимы.
При нескольких исходящих переходах выбирается физически ранний корень, а не
порядок входного списка. Неразличимые корни и нулевые каскады отклоняются.

`minimum_residence_s` — положительное ограничение модели, не менее 1e-6 с.
Для перехода нижняя граница найденного интервала корня должна отстоять от
фактического входа в режим хотя бы на эту длительность. Слишком ранний либо
неподтверждённый переход возвращает `minimum_residence` и откатывает вызов.
Событие не подавляется и не задерживается до разрешённого времени.
Частичные вызовы `advance` не обнуляют возраст режима.

Локальное смещение корня относительно численного подшага не является временем
режима. Оно может быть очень маленьким, если корень оказался рядом с границей
подшага. Для него требуется строгое представимое продвижение времени;
ограничение физического продвижения между режимами проверяется отдельно по
`minimum_residence_s`. Это устраняет ложный отказ на границе подшага, сохраняя
положительное время между переходами. Прежний бюджет одноразовых событий не
менялся. Ограничение residence относится к численному интервалу корня, а не
к строгой оценке ошибки реальной физической системы.

## Переключение и транзакция

Для активных guards переиспользуется проверка монотонности в допущенном боксе
и бисекция плотной траектории Radau. Точности локализации этого автомата:
1e-10 с по ширине интервала и 1e-10 К по значению guard. Плотная траектория
и границы события трактуются так же, как в базовом механизме: её интервал
не является строгим интервалом ошибки физической ODE.

Переход выполняет тёплую пересборку целевого режима. Температурные приращения,
их исходная система отсчёта и интеграл энергии сохраняются. Температура не
проецируется на порог. Давления/расходы могут меняться скачком в рамках
квазистационарного приближения. Прежний DP-интегратор не используется для
продолжения; конструктор режима выполняет ранее квалифицированную гидравлическую
инициализацию на текущих температурах.

Весь `advance` исполняется на отделённом кандидате. Отказ локализации, времени
режима, целевой конфигурации, области, ресурса, энергетики или финального
наблюдения откатывает все переходы и интервалы этого вызова. Ранее принятые
вызовы сохраняются. RHS, root-оценки и попытки интегрирования имеют общие
лимиты на весь вызов; счётчики не сбрасываются на смене режима.

Ограничения: 16 режимов, 32 перехода, до 16 активных guards, 128 переключений
за вызов и 4096 записей принятой истории. История не обрезается молча:
исчерпание лимита приводит к отказу. Несколько вызовов могут содержать больше
128 переходов суммарно — это проверено отдельно. Неограниченный потоковый
журнал пока не реализован.

## Остановка и восстановление

```python
first = model.advance(120.0, stop_at_transition=True)
checkpoint = model.checkpoint()
restored = HystereticRadauGraph(request)
restored.restore(checkpoint)
```

Остановка происходит на первом найденном переходе, уже в целевом режиме.
`time_s` может быть меньше `requested_time_s`; `stopped_at_transition` показывает
причину. Без перехода расчёт доходит до запрошенного времени.

Checkpoint связывает весь автомат и будущие режимы, исходники/бюджеты,
макрошаг, текущий режим и время его входа, тёплую точку входа, глобальное
состояние Radau и историю. При restore проверяются путь от начального режима,
номера записей, времена, root/residence-сертификаты, хеши команд и состояние
активного режима. Начальная температура не используется как новая догадка
для текущего режима. Продолжение проверено на точное совпадение в том же
окружении из середины цикла и непосредственно на переходе.

Восстанавливать нужно только внешний checkpoint этого класса. Вложенный
native checkpoint зависит от внешней системы отсчёта. История при restore
проверяется как согласованные метаданные; её физическое исполнение не
повторяется, хеши не удостоверяют автора. Один экземпляр рассчитан на
последовательного владельца. Состояние внешнего PID/ИИ или RNG не сохраняется.

## Квалификация и оставшиеся задачи

Девять программ до восьми узлов по 120 с: два цикла без потока, поток, реверс давления, мостовая сеть, восьмиузловые режимы,
терминальное завершение, ожидание и ветвление. 27 основных траекторий
сверяются с 18 независимыми Radau/DOP853 IVP и отдельным автоматом переключений.
Четыре ожидаемых отказа: недостаточное residence, недопустимый целевой режим,
неразличимые ветви и контакт исходящего guard при входе.

Обычные макроуровни 2/1/0.5 с; для ожидания — 1/0.5/0.25 с, для мостового
цикла — 0.5/0.25/0.125 с. Максимальные фактические пробные шаги соседних
уровней отличаются минимум в 1.2 раза. Пробные вычисления за корнем не
принимаются, но учитываются в ресурсах и метриках; эта метрика сама по себе
не доказывает сходимость каждого отдельного корня.

```bash
python -m scripts.qualify_hysteretic_radau --output artifacts/hysteresis_qualification
python -m scripts.qualify_hysteretic_radau --audit artifacts/hysteresis_qualification --output artifacts/hysteresis_audit.json
python -m examples.hysteretic_radau
```

[Пример](../examples/hysteretic_radau.py) восстанавливается на первом переходе
и продолжает многократное переключение до 120 с. Это инженерный companion;
установленный SDK runtime не изменён. Открыты произвольные guard-функции,
совмещение календаря/онлайн-команд с автоматом, приоритеты одновременных
переходов, сбросы состояния, потоковый журнал, смешанная сборка оборудования,
инерция/переменная EOS и экспериментальная/объектная валидация.
