# Дозированная подпитка через команды расхода — v143

Изменение v146: [общий PWR solver и подписи checkpoint](PWR_SPARSE_RU.md#checkpoint-и-регрессия). Протокол ниже описывает свою историческую версию; source-bound checkpoint автоматически не мигрируют.

[English](BORON_DOSING_EN.md) · [Хвост закрытия](BORON_CLOSURE_RU.md)

Новый API позволяет агенту заказать конечную массу **подпиточной воды** из
существующего бака. Содержание бора определяется баком: масса заказа не
является массой чистого бора. Планировщик учитывает текущий расход, разгон
исполнительного механизма и конечный хвост закрытия. Запасы, концентрации
и энергия не присваиваются напрямую.

## Использование

```python
from coupling.boron_dosing import plan_boron_dose, execute_boron_dose

# session — существующий BoronExchangePWRSession.
plan = plan_boron_dose(session, mass_kg=0.3, flow_kg_s=1.0)
# plan.steps() показывает все будущие команды и интервалы.
result = execute_boron_dose(session, plan)
```

Планирование не продвигает время. Выполнение делает копию сессии, подаёт
обычные команды `boron_flow_target_kg_s`, вызывает физический интегратор и
проверяет перенесённую массу обоих баков и остаточный расход. Только после
успеха всей последовательности результат фиксируется в исходной сессии.
Поздняя ошибка, в том числе неподдержанный фазовый режим, оставляет её
checkpoint неизменным.

## Что входит в план

Заказ ограничен диапазоном 0.001–100000 кг; доступный запас, давление
приёмника, время модели и бюджет истории обычно сужают его. Положительный
расход не превышает настройки модели. Закрывающийся хвост задаётся от
5 до 20 постоянных времени, по умолчанию — пять. Каждый нативный интервал
ограничен 60 с, длинная фаза разбивается на несколько команд.

Для начального расхода `q0`, команды `q`, постоянной времени `tau`,
времени открытия `T` и конечного хвоста `S`:

```text
q_close = q + (q0-q)*exp(-T/tau)
m_finite = q*T + (q0-q)*tau*(1-exp(-T/tau))
           + q_close*tau*(1-exp(-S/tau))
q_end = q_close*exp(-S/tau)
m_future = tau*q_end
```

Планировщик решает скалярное уравнение по `T` с помощью brentq. Для оценки
резерва он использует **m_finite + m_future**, а не только заказанную массу.
Неизбежный перенос уже идущего потока нельзя отменить нулевой командой:
слишком маленький заказ отклоняется. Допустим и план только закрытия,
если заказ точно равен интегралу текущего расхода за конечный хвост.

Проверяется свободный газовый объём приёмника и его предел давления 2 МПа
после всего будущего хвоста. Это оценка запасов и газового давления.
Температура, IF97-порты, насосный напор и все физические допуски проверяются
нативным solver при выполнении; они не гарантируются предварительным планом.

План связан с SHA256 полного исходного checkpoint и файлом планировщика.
Продвижение сессии, другая настройка или изменение вычисленных полей требуют
нового плана. Неподдержанные объекты и неограниченные/неконечные значения
отклоняются. Результат содержит явные команды, наблюдения и фактически
перенесённую массу. План не даёт обходного пути для изменения состояния.

## Квалификационный сценарий

Проверяются две последовательные дозы 0.3 и 0.2 кг при команде 1 кг/с,
с остаточным расходом между ними. Сравниваются подачи 0/2000 ppm и две
настройки времени: `max_step_s=0.05, rtol=2e-8` и
`max_step_s=0.025, rtol=2e-9`. Используются баки по 5000 кг, 350 К,
1 МПа, UA 500000 Вт/К, строгие жидкостные IF97-порты и сетка 2/2/4.

Независимая квадратура интегрирует точный расход, не вызывая формулу массы
планировщика. Она проверяет оба этапа каждой дозы и накопленный перенос.
Проверяются энергетические/массовые/борные балансы, независимый тепловой
эталон, EOS, энтропия и различимость борного воздействия относительно
временного шума. Два JSON-restart выполняются внутри второй дозы через
обычную нативную историю. Атомарная операция сама не приостанавливается:
ручное выполнение `plan.steps()` имеет только атомарность отдельных шагов.

Тесты отдельно проверяют невозможный заказ, остаточный хвост, снижение
команды при уже большем расходе, полное закрытие без новой открывающей
фазы, устаревший/изменённый план, ограничения, поздний отказ, испорченное
итоговое состояние и реальный неподдержанный IF97-режим. Шесть отрицательных
контролей квалификатора меняют копии результатов.

Принятая поставка: **134 целевых теста и 114 тестов из wheel**, восемь успешных фаз, полный научный JSON совпал. Шесть отрицательных контролей сработали. Максимальное временное расхождение — `2.8274612e-06`, минимальный наблюдаемый запас до насыщения — `56.003726 К`. Архивный checkpoint v142 на 61 с восстановлен точно и продолжен дозой 0.3 кг с проверкой балансов. [Машинный протокол](benchmarks/boron_dosing_v143.json).

## Воспроизведение

```sh
OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 MKL_NUM_THREADS=1 PYTHONPATH=src:. \
  python -m scripts.verify_component_delivery --component boron-dosing \
  --output artifacts/boron-dosing-local --phase-timeout-s 1200
```

Нужен новый каталог. Профиль включает целевые тесты, научный расчёт,
sdist → wheel, установку вне checkout, повтор тестов и всего научного JSON.
CI и сеть не нужны; научные зависимости переиспользуются локально.

## Границы результата

Это команда дозирования для существующего исследовательского компонента,
а не реальная СВО/САОЗ, модель растворимости, гарантия безопасности или
экспериментальная валидация. API не подключён к StationEnv. Остаются
термодинамика внутренних профилей аппарата, собственные тепловые запасы,
фазовые события с продолжением и длительная станционная квалификация.
Физические уравнения и формат checkpoint прежней модели не меняются.
Корневой статус — **58/76, открыто 18**.
