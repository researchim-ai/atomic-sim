# Локальные инструменты открытого моделёра для ИИ и LLM

> Расширение протокола 1.1 и второй backend: [публичный EOS runtime](AI_11_PUBLIC_EOS_RUNTIME_RU.md).
> Ниже сохранён исходный PWR-контракт 1.0; его действия и наблюдения поддерживаются.

Проект — open-source моделёр для исследований ИИ/RL/LLM. Клиенты, платежи
и внешний LLM-сервис не нужны для установки, запуска и проверки примеров.
Пакет `atomic_agent_tools` даёт provider-independent JSON Lines интерфейс
к существующему публичному `PWRPlantEnv`, контракт эпизода 2.1.0.
Это реальный устанавливаемый пакет и entry point, а не отдельная копия физики.

```bash
pip install -e .
python -m examples.llm_tools_episode
atomic-agent-tools
# эквивалент: python -m atomic_agent_tools
```

Пример запускает настоящий дочерний JSONL-worker и детерминированную baseline-
политику, сохраняет checkpoint, воспроизводит действие и сравнивает наблюдения.
Это демонстрация интеграции, а не оценка качества реальной LLM. Произвольный
LLM-клиент выбирает инструмент и передаёт JSON-аргументы; ни один поставщик
моделей и ни одна сеть API не зашиты в расчётный процесс.

## Протокол 1.0.0

Каждая UTF-8 строка stdin содержит один запрос; stdout содержит только одну
JSON-строку ответа на него. stderr отведён диагностике. Это собственный
локальный JSONL-протокол, не MCP и не JSON-RPC. Каталог возвращает имена,
описания и input_schema в подмножестве JSON Schema 2020-12.

```json
{"request_id":"r1","tool":"describe_simulator","arguments":{}}
{"request_id":"r2","tool":"create_episode","arguments":{"session_id":"episode","config":{"seed":42,"episode_horizon_s":0.03,"action_dt_s":0.01}}}
```

`create_episode` возвращает `revision`, `observation_id` и массив измерений
с именем, единицей, quality-флагом, временем выборки и признаком насыщения.
`inspect_episode` читает кеш: физика, датчики и RNG не продвигаются.
Поддержан ограниченный PWR-паспорт; доступность произвольных реакторов или
экспериментальных EOS-сборок через этот endpoint не заявлена.

Для `step_episode` агент копирует **оба** guard-поля из последнего ответа:

```python
args = {
    "session_id": view["session_id"],
    "expected_revision": view["revision"],
    "observation_id": view["observation_id"],
    "action": {"rod_command": 0.001},
}
```

Действие именованное, в физических единицах, без скрытой нормализации.
Оно содержит ровно каналы `config.action_channels`. Каталог/наблюдение
публикуют допустимые диапазоны и единицы: rod_command — 1/s, throttle — 1,
feed_bias_kg_s — kg/s, boron_ppm — ppm, sink_temperature_k — K.
Числовые bool, NaN/Infinity, неизвестные поля и неполные маски отклоняются.

Все операции worker сериализованы. Для изменения эпизода нужны актуальные
revision и observation_id. Restore увеличивает ревизию, а создание с тем же
именем после close получает новую генерацию токена. Старое наблюдение нельзя
повторно использовать для действия после перемотки или пересоздания.
`request_id` — корреляция ответа, а не idempotency key; повтор старого действия
отклоняется guard-проверкой и не выполняется второй раз.

## Инструменты и наблюдаемость

- `describe_simulator`: каталог, единицы, лимиты, паспорт и provenance.
- `create_episode` / `inspect_episode` / `step_episode`: жизненный цикл и действие.
- `save_checkpoint`: непрозрачный checkpoint_id, без внутреннего состояния.
- `restore_checkpoint`: восстановление handle с новой ревизией и наблюдением.
- `cancel_episode`: отмена между вызовами с сохранением физических запасов.
- `close_episode`: освобождение сессии.
- `forget_checkpoint`: явное освобождение checkpoint handle.

Агент получает только четыре публичных сенсорных канала и результат перехода,
а не истинный вектор состояния, состояния датчиков/RNG или evaluator-метрики.
Контрольная плоскость Python-хоста отдельно умеет `export_session` и
`import_session`: это **не** инструменты каталога LLM. Полный checkpoint
содержит внутренние данные и должен храниться отдельно от контекста агента.
Это разделение интерфейсов, не sandbox против кода, уже исполняемого на хосте.

Физическая ошибка среды сохраняется как failed-эпизод с `truncated=true`,
`terminated=false`, причиной domain/model/solver и исходным failure reward.
Достижение горизонта — completed/time_limit; task_terminal — семантика задачи.
Ошибка аргумента оставляет модель, сенсоры и RNG неизменными. Ошибка программы
возвращает internal_error и пишется в stderr, не маскируется под физический отказ.

## Воспроизведение и границы атомарности

Каждое действие выполняется на восстановленной копии публичного native episode.
Расчётная семантика совпадает с публичным `agent_envs.replay.continue_episode`;
результаты этого маршрута сравниваются точно, включая шум и RNG. Прямое
продолжение живого объекта без сериализации может иметь отличия округления
в производных величинах; побитовая эквивалентность этому другому маршруту не
заявлена. Контракт модели и физические уравнения не изменены.

Checkpoint по handle хранится в памяти worker. Для нового процесса хост
сохраняет/загружает полное состояние явно:

```bash
atomic-agent-tools --checkpoint-out episode.json --session-id episode
# После create/step завершить stdin; хостовый файл создаётся при EOF.
atomic-agent-tools --resume episode.json --session-id episode
```

Пути разрешены только флагами хостового CLI, не аргументами инструментов.
Выход создаётся без перезаписи: сначала полный временный JSON, затем
эксклюзивная публикация. Импорт проверяет checksum, источники/версии, native
контракт, поддержанную конфигурацию и согласованность lifecycle/флагов.
Новый worker получает новую генерацию observation_id; агент перечитывает
наблюдение перед действием. SHA — целостность, а не подпись/аутентификация.
Точное продолжение подтверждается в совместимой локальной среде; не обещается
побитовое совпадение между произвольными ОС и версиями библиотек.

Лимиты worker: 8 сессий, 32 checkpoint, до 4 MiB на checkpoint и 16 MiB суммарно,
4096 запросов/модельных транзакций, 1024 решения на эпизод. Горизонт до 10 s,
шаг действия 0.001–0.05 s; конфигурация, требующая больше допустимых решений,
отклоняется. Неуспешные запросы расходуют request quota, начатые модельные
операции — model quota. Restore/close не возвращают израсходованную квоту.
При заполнении checkpoint-store требуется явный forget, скрытого вытеснения нет.

Worker синхронен; cancel действует между решениями и не прерывает блокирующий
native solver. Лимиты транзакций не являются hard wall-time лимитом; для такого
лимита нужен отдельный process supervisor. Удалённый сервис, распределённые
jobs, произвольный model registry, редактор топологии, исполнение policy-кода
и весь AI-11 этим интерфейсом не закрываются.

## Что проверяется

Тесты сопоставляют действия и сенсоры с публичным replay, проверяют stale/ABA,
шум/RNG, ошибки схемы/конфигурации, конечный горизонт, lifecycle, переполнение
ресурсов, отказ программы/модели, приватность checkpoint и конкурентные действия.
Отдельные subprocess-тесты проверяют повреждённый/повторный/большой JSON,
UTF-8, продолжение обработки после ошибки, хостовое сохранение и новый процесс.
Каталог отдельно проходит стандартный JSON Schema validator в dev-среде.

Wheel устанавливается офлайн вне checkout без загрузки зависимостей; затем
проверяются импорт из установленного wheel, консольный entry point, тесты и
пример. Научные зависимости среды унаследованы, это не герметичный контейнер.
Материалы — `validation/ai11_agent_tools_delivery_v1.json` и
`validation/ai11_agent_tools_portable_replay_v1.json`. Публикация в PyPI/GitHub
и запуск внешней LLM не выполняются. Численные claims ядра остаются прежними:
новый протокол не делает модель validated/plant_referenced.
