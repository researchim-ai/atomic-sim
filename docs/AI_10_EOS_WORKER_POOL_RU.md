# Ограниченный пул EOS worker без изменения численной модели

`atomic_model_pool` 1.0.0 сравнивает прежний `atomic_model_bench` с повторным
использованием доверенных процессов. Новый `EOSEpisode` создаётся для **каждого**
случая. Переиспользуются интерпретатор и импортированные библиотеки; состояние
среды, история команд, clock и checkpoint между случаями не переносятся.

```bash
atomic-model-pool examples/eos_pool_comparison.json --output artifacts/eos_pool
# либо
python -m atomic_model_pool examples/eos_pool_comparison.json --output artifacts/eos_pool
```

Schema1: `performance` — прежняя строгая схема benchmark; дополнительно
`max_cases_per_worker` в диапазоне 1..64 ограничивает срок повторного
использования процесса. Неизвестные поля/модули/версии, недопустимые мощности,
seeds, CPU/RSS/deadline отклоняются до создания выходного каталога. Он должен
быть новым. Не происходит загрузки пользовательского Python, executable,
модели или policy plugin из JSON.

## Почему именно эта оптимизация

Замороженный предыдущий workload: восемь коротких случаев, два повтора,
1/2/4/8 worker на общем бюджете двух CPU. Импорт/инициализация и подготовка
вывода заметны относительно короткого физического горизонта. Поэтому проверяется
издержка нового интерпретатора на каждый case. Предыдущие драйверы, EOS, SSPRK3,
шаги, admission и балансовые допуски не изменены. Это оптимизация инфраструктуры
запуска, а не оптимизированная или аппроксимированная физика.

В baseline для каждого case остаётся прежний отдельный subprocess. В pool-mode
процесс получает ровно один активный запрос, исполняет тот же `worker.run`,
возвращает полный native episode, затем может принять следующий. Каждая новая
trial начинает с новых worker: первый startup, импорт, все случаи и конечное
завершение процессов включены в trial wall time. Речь о новых интерпретаторах,
не о гарантированно холодном filesystem/page cache ОС.

Порядок classic/pool чередуется между повторами. У режимов одинаковые cases,
actions, horizon, max_step, source, число worker и общее CPU-выделение. Все
существующие потоки supervisor и дочерние процессы ограничены одним CPU set.
Новые numerical worker получают OMP/OpenBLAS/MKL/NumExpr=1 до импортов.

## Протокол и изоляция отказа

Mailbox — ограниченная строка JSON с путями к request/result и task token.
Результат публикуется атомарно. Supervisor проверяет token, source пула,
неизменённый baseline source, CPU/thread-настройки, config, команды, полный
horizon, native checkpoint и его digest. Поздний или чужой result нельзя принять
за другую задачу. Pool source повторно проверяется перед каждым запросом.

На crash, deadline, RSS-превышение или неверный completion процесс завершается,
его результат не считается завершённым episode; следующие случаи получают
новый worker. Повторное использование ограничено task cap. Повтор задания после
ошибки автоматически не выполняется: нельзя скрыть отказ удачным retry.
Исходы всех случаев сохраняются. Speedup вычисляется только для полных trials
с одинаковыми native episode hashes. При исключении supervisor его живые workers
останавливаются в `finally`; старые результаты не перезаписываются.

RSS-budget наблюдаемый, не cgroup/hard OS memory quota. Kernel peak RSS в
постоянном worker относится ко **всей жизни процесса**, не отдельному case.
Порог текущего RSS проверяется для занятого worker; idle RSS входит в
наблюдаемую агрегированную метрику. Garbage collection
после case не обещает возврата всех страниц ОС; поэтому task cap и рестарт при
превышении остаются обязательными. Нет недоверенного кода и его OS sandbox.

## Метрики и доказательства

В report — end-to-end throughput, simulated seconds/wall second, интерполированные
p50/p95, sampled aggregate RSS, per-case RSS peak, PID/worker_index/task ordinal,
число созданных процессов, измеренное время первого импорта worker и фазы
каждого расчёта. Первоначальный импорт выполняется при установке worker identity;
`worker_startup_wall_s` показывает его стоимость. `import_wall_s` внутри run
может быть близок к нулю уже на первом case, потому что библиотеки загружены
на этапе startup. Trial wall включает оба этапа. Case latency отсчитывается с запуска процесса для первого назначения
или dispatch для повторного. Время в общей очереди до назначения не входит.
Проверка supervisor входит в общий trial wall, но не в latency, зафиксированную
до admission.

Каждый pool episode сравнивается с classic и остальными повторами на уровне
канонического native JSON digest. Тест возврата к исходным условиям после другого
case дополнительно проверяет отсутствие переноса model/history state.

Порог speedup 2x объявлен в коде до измерений и сравнивает pool с classic **при
том же числе worker**. Это отдельный показатель от предыдущего scaling относительно
одного worker. Восемь worker на восемь cases могут не переиспользовать процессы;
пул не объявляется автоматически быстрее. Два повтора дают контрольный замер,
а не надёжную оценку производительности на любых машинах или длинных задачах.

Нет полного Gym/vector environment API, checkpoint/resume всего performance-run,
learner API или произвольных policy plugins. Долговечные задания с pause/resume
остаются в отдельном `atomic_model_workspace`; они этим пакетом не заменяются.
Будущая работа: persistent rollout API, ограничения ресурсов ОС и оптимизация
самого ядра по профилю. `validated=false`, `plant_referenced=false`.

## Локальный парный результат v1

128 полных эпизодов: 8 cases × 4 worker counts × 2 режима × 2 повтора.
Все native checkpoints совпали между режимами и повторами. Median throughput
для одного worker: classic ~1.96 episode/s, pool ~3.13 (speedup **1.597x**).
Для двух: ~3.36 → ~5.12 (1.525x); четырёх: ~4.04 → ~4.34 (1.074x);
восьми: ~3.54 → ~3.17 (0.895x, то есть замедление). Ускорение не универсально;
строгий критерий 2x при одинаковом worker count не выполнен.
Машинный summary: `validation/ai10_eos_pool_summary_v1.json`.
