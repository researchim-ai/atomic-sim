# Непрерывный цикл подготовки горячего состояния и выдержки

`atomic_model_station_hot` связывает прогрев, проверку готовности и
последующую выдержку в одну воспроизводимую программу. Обе фазы продолжают
одну историю `FaultSession`: переход не назначает массы, энергию,
давление, позиции приводов или память PI и не обнуляет часы.

В штатном профиле используются шесть автоматических контуров, цель
мощности 3,15 ГВт и нейтральная полоса питания 0,2 мм. Точное время
подготовки не назначается заранее как «стационар»: готовность должна
возникнуть по результату расчёта.

## Условия перехода

Начальная фаза — `warmup`. На каждом принятом такте сохраняются полный
вектор состояния, измерительный кадр, команды, локальные запасы и их RHS.
Проверка готовности использует полное скользящее окно с достаточной
частотой отсчётов. Из вектора исключаются только семь накопительных
энергетических счётчиков; вода и энергия резервов остаются в проверке.

Штатные условия прежние: окно 600 с, максимальный нормированный размах
1e-3, накопление энергии относительно мощности не более 1e-3, штатные
допуски балансов и измеренных заданий. Начало и конец окна не заменяют
проверку всех его отсчётов. До появления полного окна готовность отрицательна.

Дополнительно проверяются локальные водяные невязки и общая производная
массы с допуском 1e-9 кг/с. Защёлкнутая защита, физический отказ или
превышение балансовых допусков завершают программу отказом.

После положительной готовности проверяется остаток обоих бюджетов:
физического времени и журнала. Только затем начинается фаза `hold`.
Её критерии проверяются на каждом такте, включая окна, пересекающие
границу прогрева. Потеря готовности даёт `hold_readiness_lost`, а не
повторное скрытое назначение начального состояния.

Если предел прогрева исчерпан, фаза становится `unprepared` с причиной
`warmup_exhausted`. Выдержка не начинается. При отклонении следующего
такта сохраняется последний принятый физический префикс без выдуманного
продвижения времени. При потере готовности после принятого такта его
физическое состояние сохраняется — часы не откатываются ради приёмки.

## Бюджеты и смысл результата

Суммарный запрошенный прогрев и выдержка ограничены 7200 с и 8192 тактами.
Длительности и окно должны состоять из целых тактов. Окно содержит как
минимум три отсчёта; частота должна удовлетворять `maximum_gap_s`.
Несовместимая конфигурация отклоняется до расчёта.

`hold_passed` означает завершение выдержки по явно заданным условиям.
`canonical_hold_passed` требует также штатных критериев, штатной цели
мощности и не менее 3600 с выдержки. Короткие тестовые окна и ослабленные
исследовательские настройки не получают этот флаг.

Один путь даже с `canonical_hold_passed=True` не является полной приёмкой
станции: ещё нужны уточнение, restart, установленный повтор и остальные
режимы R1. Поэтому библиотечный цикл сам не выставляет
`stationary_accepted=True` и не закрывает задачи NPP-11.

## Использование

```python
from atomic_model_station_hot import HotConfig, HotSession

run = HotSession(HotConfig(maximum_warmup_s=3600., hold_s=3600.))
while not run.finished:
    status = run.step()
saved = run.checkpoint()
```

Каждый такт транзакционен: ошибка вычисления нового состояния или его
диагностики не меняет принятый физический владелец. Экспортированные
checkpoint и отчёты не дают изменять внутреннюю историю через общие ссылки.
Данные включают привилегированное состояние разработчика; это не новые
скрытые каналы наблюдения агента.

CLI сначала сохраняет протокол, затем отдельные checkpoint через каждые
20 попыток и окончательный отчёт:

```bash
export OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 MKL_NUM_THREADS=1
export PYTHONPATH="$PWD/src"
python -m atomic_model_station_hot \
  --output artifacts/hot-full-new --maximum-warmup-s 3600 --hold-s 3600
```

Для ограниченного исследовательского прогона:

```bash
python -m atomic_model_station_hot \
  --output artifacts/hot-screen-new --maximum-warmup-s 1200 --hold-s 3600
```

Вторая команда действительно допускает выдержку после подтверждённой
готовности; она не принудительно останавливается на 1200 с. Если прогрев
не готов, она завершается на его границе. Код выхода 0 означает завершённую
выдержку, 2 — явный отказ/неготовность; ошибка входа также не выдаётся за
успешную приёмку. Для фактической оценки нужно читать `report.json`.

## Restart всей программы

Checkpoint хранит конфигурацию, число попыток, журнал измеренных и
физических данных, состояние фаз и checkpoint всей станции. `HotSession.restore`
заново исполняет принятый префикс и сравнивает полный результат. Это также
проверяет происхождение готовности, а не доверяет присланному флагу `ready`.
Стоимость восстановления включает повтор префикса.

```bash
python -m atomic_model_station_hot \
  --resume artifacts/hot-full-new/checkpoint-00120.json \
  --output artifacts/hot-resumed-new
```

При resume конфигурационные флаги запрещены: параметры берутся из
проверенного checkpoint. Незавершённый цикл продолжается с прежних часов
и PI. Терминальный checkpoint воспроизводит уже полученный исход, а не
продлевает прежний лимит прогрева. Изменение условий требует отдельной
объявленной программы.

## Проверка реализации и граница физического свидетельства

Короткие связанные тесты намеренно используют окно 0,02 с, другую цель
мощности и мягкий допуск размаха: это позволяет проверить обе фазы, их
транзакции и restart без фиктивного объявления промышленного стационара.
Такие случаи явно имеют `canonical_criteria=False` и
`stationary_accepted=False`. Отдельный строгий случай должен отказать
в запуске выдержки.

```bash
python -m pytest tests/test_station_hot.py
python -m scripts.qualify_station_hot_state --output artifacts/hot-study-new
python -m scripts.verify_local_library --output artifacts/hot-library-new
python -m scripts.verify_station_inventory_delivery --study hot_state \
  --output artifacts/hot-installed-new \
  --source-evidence artifacts/hot-study-new \
  --library-evidence artifacts/hot-library-new
```

Проверка wheel заново исполняет эти случаи вне исходной копии, сравнивает
все научные JSON и запускает установленный CLI с resume из фазы прогрева.
Его конечный checkpoint должен точно совпасть с непрерывным коротким путём.
Этот тест не подменяет численную квалификацию длительного горячего состояния.
Длительный исследовательский прогон оценивается отдельно по его протоколу,
сохранённым физическим состояниям и фактическому исходу.


## Результат v58

[Машинный отчёт](benchmarks/station_hot_lifecycle_v58.json) разделяет
проверку программы и физический исход длительного прогона. 19 новых
тестов прошли; профиль библиотеки — 1851 тест и восемь фаз.
В коротких фикстурах максимальное расхождение уточнения составило
2.42721562e-07; оба restart и все 15 научных JSON
повторены точно из wheel. Установленный CLI восстановил прогрев и дал
тот же конечный checkpoint, что непрерывная короткая программа.

Строгий исследовательский прогон с целью 3,15 ГВт, полосой 0,2 мм,
тактом 5 с и окном 600 с завершился на 1200 с: `unprepared`,
`warmup_exhausted`. Приняты все 240 физических тактов, но готовность
не получена, выдержка не начиналась. Последнее окно — 600–1200 с,
121 отсчёт. Максимальный нормированный размах —
0.790240106 при допуске 0,001.
Крупнейшие изменения: surge.flow, drain.energy и drain.mass.
Максимальная относительная мощность накопления энергии в окне —
0.00663891905 при 0,001.
Общие балансы и локальные водяные невязки соблюдены: это дрейф
физического состояния, а не признанная утечка или переписанный запас.
Во всех 121 отсчёте последнего окна измеренные задания удовлетворяли
своим допускам. Тем не менее полный физический вектор и мощность
накопления энергии не прошли проверку стационара.

В этом длинном пути пока не выполнены уточнение, restart или установленный
повтор. Его отрицательный физический исход не заменяется успешными
короткими тестами инфраструктуры. Нейтральная полоса сама по себе не
закрыла задачу: дальше нужно согласованное горячее состояние с полным
тепловым балансом, включая работу насосов, потери и теплоотвод, затем
полная численная проверка нового hold. Счётчик остаётся 46/76, R1 открыт.
