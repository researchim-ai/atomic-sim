# Совместная EOS-сборка: конечные запасы, стенка и онлайн-нагрев

`ControlledEOSAssembly` объединяет два гидравлически изолированных контура
с конечными торцевыми объёмами и теплоёмкие стенки. В каждой жидкости
сохраняются масса, импульс, полная энергия с кинетической и гравитационной
частями; стенки имеют собственный энергетический запас. Теперь эти части
интегрируются совместно, а не запускаются отдельными демонстрациями.

```bash
python -m examples.controlled_eos_assembly
python -m pytest -q tests/test_controlled_eos_assembly.py tests/test_controlled_assembly_audit.py
python -m scripts.qualify_controlled_assembly run artifacts/ai05_controlled_assembly_campaign_v1.json
python -m scripts.qualify_controlled_assembly audit artifacts/ai05_controlled_assembly_campaign_v1.json
```

## Сборка и тепловые порты

Вход содержит ровно два именованных контура `primary` и `secondary`, каждый
в формате `atomic-terminal-eos-chambers`. Их сетки и синтетические калорические
EOS могут различаться; массового обмена между контурами нет. Каждый контур
по-прежнему имеет общее сечение канала и торцевых объёмов и неподвижные
отражающие внешние стенки. Реакция внешних стенок учитывается локально в
импульсном журнале каждого контура.

Тепловая стенка задаёт уникальный ID, теплоёмкость C, Tw0, две положительные
UA, собственный нагрев и теплообмен со средой. Два порта должны принадлежать
разным контурам. Версионируемая схема порта разрешает только:

```json
{"circuit":"primary","component":"channel","cell":1}
```

или

```json
{"circuit":"secondary","component":"chamber","side":"left"}
```

Неизвестные компоненты, ячейки, стороны, поля и повторные ID отклоняются до
расчёта. Несколько стенок могут подключаться к одному порту; суммируются
и потоки, и тепловая нагрузка при выборе шага. Это ограниченный реестр
тепловых соединений, а не произвольная гидравлическая топология или плагинный
реестр оборудования. Механические напряжения и силы общей стенки не моделируются.

## Совместные балансы

Для каждого соединения Q=UA*(Tw-Tfluid). Ровно тот же Q входит в жидкость
и уходит из стенки. Локальный журнал жидкости считает его внешним для этой
подсистемы; общий журнал вычитает внутренний перенос из внешнего нагрева.
Стенка может получать собственную внешнюю мощность и обмениваться теплом
со средой. Численная диссипация каждого гидравлического контура сохраняется
в его энергетическом/энтропийном журнале.

Энтропия стенки меняется на C*ln(Tw/Tw0); производство на контакте равно
Q*(1/Tfluid-1/Tw). Общий журнал исключает внутренний перенос энтропии и
учитывает производство на контактах и при обмене со средой. Контролируются
балансы массы и импульса каждого контура и суммарные энергия/энтропия всей
сборки. Существенно отрицательное производство или превышение допуска
приводит к отказу. Общего доказательства энтропийной устойчивости Euler-схемы
для всех начальных данных нет.

SSPRK3 одновременно обновляет жидкости, торцевые объёмы, стенки и журналы.
Акустические размеры и суммарные UA/(m*cv) проверяются на стадиях. Для стенки
используется (sum(UA)+UAambient)/C. Пространственная схема первого порядка;
метод явный, не all-speed, implicit или IMEX. Ограничение устойчивости не
заменяет оценку временной точности; пользователю может потребоваться меньший шаг.

## Команды управления

`snapshot()` публикует `port_temperatures_k`, `active_heat_power_w`, ревизию,
историю, состояния контуров и стенок, общие балансы. Ключи полной маски
внешних мощностей имеют вид `primary.channel.c0`, `secondary.chamber.left`,
`wall.w0`. Мощности измеряются в W, температуры в K. Положительное значение
нагревает, отрицательное отводит тепло. Это заданный тепловой поток: модель
не рассчитывает КПД, электрическое питание, COP или динамику исполнительного
механизма. Температура среды и UA не меняются командами.

```python
observation = assembly.snapshot()
powers = observation["active_heat_power_w"].copy()
powers["primary.chamber.right"] = 1000.0
result = assembly.step(powers, 0.05,
    expected_revision=observation["revision"], command_id="heater.change")
```

Маска должна содержать все нагреватели без лишних ключей. ID уникален в
истории эпизода; неверная ревизия, маска, ID, длительность или ошибка стадии
не меняет физические состояния, журналы, мощность, историю и ревизию.
Команда не скачком меняет энергию: в `heater_transition` физические запасы
на левой/правой стороне переключения одинаковы. Изменяется только будущая
правая часть. Это диагностические переходные наблюдения; актуальная ревизия
для следующей команды находится в основном результате.

Операции одного экземпляра защищены reentrant lock: проверка ревизии,
интегрирование и commit сериализованы. Две конкурирующие команды с одной
ревизией не могут обе зафиксироваться; два advance не теряют время.
Это внутрипроцессная синхронизация объекта, а не распределённая транзакция.
Восстановлением управляет владелец эпизода; после restore клиент получает
свежее наблюдение. Числовая ревизия не является распределённым fencing token.
Публичные наблюдения/checkpoint/residual используют ту же блокировку;
временные представления компонентов не меняют исходные подсистемы.

## Restart и свидетельства

Checkpoint включает все рабочие координаты, источники, бюджет, входы, шаг,
активную полную маску и квитанции команд. Restore проверяет последовательность,
время, commit-ревизии, уникальность ID, соответствие последней маски и
восстановленного наблюдения. Точный JSON-restart подтверждён в одной среде.
SHA — контроль случайного повреждения, не подпись истории. Чистый residual
не меняет состояния или контроллер. Собственного PID/ИИ-регулятора,
автоматических guard/event-переключений и состояния внешнего контроллера
в этой сборке пока нет: контроллер вызывает API между шагами.

Восемь программ: равномерная аналитическая постановка, смешанные порты,
движение/отражение, гравитация, большой p_inf, теплообмен со средой, разные
сетки и онлайн-команда. Три ограничения шага, пять наблюдений до 0.1 s:
24 траектории, 120 наблюдений, 16 независимых программ DOP853/Radau и
80 solve_ivp-сегментов. Команда выполняется на 0.05 s после сохранения
checkpoint; точное продолжение проверяет также историю и активную маску.
Независимая сборка использует абсолютные m/P/E и собственное соединение
тепловых портов поверх независимой модели торцевых объёмов/Euler-канала.
Это проверка временной интеграции полудискретной модели, не физическая аттестация.

Аналитический тест сопоставляет одинаковые тепловые тройки с матричной
экспонентой; отдельный тест включает ступень внешнего нагрева и проверяет
изменение полной энергии. Проверяются дефекты журналов, маски и checkpoint,
прямые конкурентные вызовы, обратимый порядок портов, повторные подключения,
разные калорические жидкости и сохранение отдельной массы каждого контура.
Аудитор проверяет источники, полную матрицу, допуски, метрики, фактически
различные шаги и ожидаемую итоговую маску управления. Полные масштабируемые
балансовые допуски проверяет движок; по максимумам отчёта нельзя восстановить
все масштабы. Аудит не повторяет интегрирование и не удостоверяет автора.

Переносимая проверка публикуется в
`validation/ai05_controlled_assembly_portable_replay_v1.json`: офлайн-wheel,
архивный аудит, тесты и пример вне checkout с унаследованными numpy/scipy/pytest.
Это не герметичная среда, межплатформенная проверка или повтор всей кампании.
Полный репозиторный прогон нового семейства не выполнен; прежний полный
software-baseline сохраняется. Старые квалифицированные драйверы не изменены.

Ограничения: два контура, до 64 внутренних ячеек суммарно, до 16 стенок,
Mach≤0.2, синтетическая EOS. Нет произвольных баков/пленумов/сопел,
гидравлического ветвления, фазовых границ, IAPWS-калибровки, публичной SDK-
интеграции или объектной валидации. AI-05.03/07/08 остаются открыты;
validated=false, plant_referenced=false.
