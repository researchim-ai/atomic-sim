# Точность длительных PWR-переходов: шаг и допуски

> Ранние исторические результаты ниже получены до исправления коэффициента n21 IF97
> во внешнем benchmark 9 ноября 2026. Их source-bound приёмка автоматически
> не перенесена на новое ядро. Актуальные повторные проверки указаны в
> [текущем статусе](CURRENT_STATUS_RU.md) и
> [протоколе внешнего сравнения](EXTERNAL_BENCHMARK_RU.md).


Профиль `scripts.verify_pwr_refinement` проверяет связанную исследовательскую
конфигурацию `pwr-reduced-flow-controlled`. Он дополняет точный replay:
повторяемость одного расчёта сама по себе не оценивает численную ошибку.

## Воспроизведение

```bash
python -m scripts.verify_pwr_refinement --output artifacts/pwr-refinement-local --jobs 2
```

Нужен новый каталог. Доступны 1–4 независимых процесса; `--timeout` ограничивает
каждый расчёт по настенному времени, по умолчанию 7200 с. Прерванные и отказавшие
результаты сохраняются. `--cases scram` выбирает поднабор и не считается полной
матрицей. Прогон длительный и не включается неявно в быструю проверку поставки.

Каждый процесс кампании запускается с `OMP_NUM_THREADS=1`,
`OPENBLAS_NUM_THREADS=1`, `MKL_NUM_THREADS=1`. Для прямого replay полученного
checkpoint следует сохранять эти настройки; один и тот же номер версии
NumPy/SciPy сам по себе не фиксирует число потоков BLAS.

Продолжение в новом каталоге:

```bash
python -m scripts.verify_pwr_refinement --output artifacts/pwr-refinement-resumed --reuse-from artifacts/pwr-refinement-local --jobs 2
```

## Строгий сброс: ограниченные окна численной истории

Первый непрерывный строгий Radau-сброс остановился на 2930 с с
`Hybrid RHS budget exhausted`: лимит 500000 вычислений относится к накопленной
истории решателя. Отказ и частичная траектория сохранены в
`artifacts/pwr-refinement-v1/load_rejection_equilibrium--reference/`.
Полный горизонт по этой пробе не принимается.

Для строгого сброса используется явно объявленный `run_pwr_windowed_reference`:
каждые 500 с очищается только численная история решателя. Физическое состояние,
активные ограничения, время, управляющая программа и накопленные балансы
не изменяются. До/после очистки проверяется точное совпадение хеша состояния
и checkpoint. Следующий вызов записывает штатный `reset_solver_before_step`,
который уже поддерживает `Session.restore`. Бюджет внутренних вычислений
не отключён, состояния не проецируются, допуски 1e-8/1e-7 и предел 0,5 с
не ослаблены. Первое окно и каждое последующее выполняются тем же Radau.

```bash
OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 MKL_NUM_THREADS=1 \
  python -m scripts.run_pwr_windowed_reference --output artifacts/strict-windowed
python -m scripts.verify_pwr_refinement --output artifacts/refinement-readmitted \
  --reuse-from artifacts/pwr-refinement-local --reference-from artifacts/strict-windowed
```

Приёмка проверяет хеш отдельного worker, весь список 14 окон, неизменность
состояния на каждой границе и запись соответствующих сбросов в checkpoint.
Старые завершённые расчёты заново допускаются; частичный непрерывный ориентир
не подменяется положительным результатом. Автоматический полный профиль сам
выбирает оконный worker только для строгого сброса. Критерии полного горизонта,
балансов и установления совпадают с обычной кампанией.

Состояние на 9 ноября: оконный запуск прерван на 6545/7200 с, его процесс
не сохранился. Итогового checkpoint нет; префикс не принят как полный расчёт.
Все 15 завершённых исходных расчётов отдельно повторно допущены, три полных
сравнения точности прошли (`artifacts/pwr-completed-readmission-v1/report.json`).

В новых запусках worker сохраняет `progress-checkpoints/step-NNNNNN.json`
на каждом интервале 500 с и в конце. Атомарная запечатанная квитанция содержит
checkpoint Session, исходную идентичность, хеш worker, журнал сбросов,
размеры в байтах и SHA256 префиксов обоих уже сброшенных на диск логов.
После роста логов проверяется соответствующий префикс указанной длины.
Квитанции не перезаписываются и всегда имеют `full_horizon_accepted=false`.
Восстановление checkpoint требует `Session.restore` и проигрывания истории;
это не быстрый снимок решателя. Продолжение выполняется в новую директорию:

```bash
OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 MKL_NUM_THREADS=1 \
  python -m scripts.run_pwr_windowed_reference \
  --resume-from artifacts/strict-windowed/progress-checkpoints/step-000100.json \
  --output artifacts/strict-windowed-resumed
```

Проверяются печать квитанции, версия worker и физического кода, настройки,
граница окна, размеры/хеши префиксов, команды, длительности шагов, журнал
сбросов и соответствие хешей состояния. После этого выполняется точный
`Session.restore`; конечные наблюдения тоже должны совпасть. Дополнительные
байты после сохранённого префикса игнорируются: в новую директорию копируется
только проверенный префикс. Восстанавливаются события и экстремумы от начала
расчёта; исходная директория не изменяется. `resume-origin.json` связывает
новый расчёт с исходной квитанцией. Полный горизонт и прежние критерии
проверяются после продолжения. Финальная квитанция также допускается:
она воспроизводит результат без добавления новых шагов.
Старый префикс не дополнен квитанциями задним числом. Изменение worker
меняет его хеш; старые проверки границы относятся к прежней версии worker.

Граница первого окна отдельно проверена из установленного wheel вне checkout:
из сохранённой исходной истории построен и запечатан checkpoint-префикс
на 500 с, выполнен полный replay этого префикса, затем очистка численной
истории и интервал 500→505 с. Хеши совпали точно с оконным расчётом.
Отчёт: `artifacts/installed-window-restart-v1/report.json`.
Это проверка границы окна и префикса, не заявление о полном replay 7200 с.

Оконный и исходный непрерывный строгие расчёты отдельно сопоставлены на
общем префиксе 0→2930 с: все 587 отсчётов сохранены, численные различия
уложились в исходные бюджеты. Максимальная доля бюджета — 3,52e-9.
Отчёт: `artifacts/pwr-window-prefix-comparison-v1/report.json`.
Это чувствительность численных наблюдений к перезапускам; итоговая
приёмка 7200 с и топология событий этим префиксом не подтверждаются.

Поддержанные версии алгоритмов проверены также отдельным полным SCRAM
BDF/Radau при одинаковых строгих допусках. Сравнение относится к одному
исследовательскому сценарию с общей EOS и уравнениями; оно не делает BDF
квалифицированным для всех PWR-сценариев и не является экспериментом.

## Повторный допуск

Повторное использование требует идентичных физических условий, настроек,
критериев, исходников модели и admission-проверки. Версия самого управляющего
скрипта может отличаться; её прежний хеш сохраняется в записи повторного
использования. Каждый
завершённый случай заново проверяется по собственному результату, балансам,
контрольным суммам trace/наблюдений/checkpoint, временной сетке, настройкам
решателя и журналу команд/событий. Повреждённый случай рассчитывается заново.
При изменении физических условий или критериев следует выполнять новую кампанию.

## Что сравнивается

Четыре полных горизонта: SCRAM 60 с, выбег 1800 с, естественная циркуляция
1800 с, установление после сброса нагрузки 7200 с. Для каждого:

- Radau, `rtol=1e-6`, `atol=1e-5`, ограничения внутреннего шага 2 / 1 / 0,5 с;
- отдельный конечный численный ориентир: Radau, 0,5 с, `rtol=1e-8`, `atol=1e-7`.

Это адаптивный решатель: ограничение шага не означает, что каждый шаг имеет
эту длину. Поэтому профиль разделяет чувствительность к ограничению шага
и к допускам; он не выводит порядок Ричардсона и не обещает точную ошибку
непрерывного решения. Материальная база и уравнения у ориентиров общие.

Наблюдения сохраняются в `observations.jsonl` от начального состояния до
полного горизонта с интервалом 5 с. Сравнивается каждая точка одинаковой сетки;
интерполяция и пересечение с потерей отсутствующих отсчётов не допускаются.
Отчёт содержит максимальное различие, его время, различие конечных значений
и выборочных экстремумов для мощности деления/тепловой мощности, температур
топлива/активной зоны/холодной нитки, первичного/вторичного давления, расходов,
хода поглотителя, реактивности и скорости вала. Между отсчётами могут быть
неразрешённые пики; этот профиль не оценивает их величину.

Бюджеты объявлены до расчёта в `BUDGETS`: 0,1 К для температур; 1600/640 Па
для давлений; 310 кВт для мощностей; 1,8 кг/с первичного и 0,1 кг/с вторичных
расходов; 1e-5 хода, 1e-6 реактивности и 0,01 рад/с. Это критерии численного
сравнения, а не экспериментальные неопределённости и не критерии безопасности.
Проверяются сравнения с более строгим ориентиром и соседних ограничений шага.

Корни штатных событий сравниваются отдельно: одинаковый типовой состав
в хронологическом порядке и различие времени не более 0,02 с. Состояния
защёлки SCRAM должны совпадать на всей сетке. Отсутствие события в одной
траектории является отказом, даже если конечные значения близки.

Каждый исходный расчёт сначала должен пройти прежние полные критерии
`qualification.CASES/CRITERIA`, включая балансы и установление сброса.
Частичный горизонт не допускается к сравнению. `report.json` и протокол
запечатаны, `progress.json` отражает завершённые процессы. Код возврата
неуспешной кампании — 1. Численная приёмка не изменяет `validated=false`
и `plant_referenced=false`.

Расширение формата диагностики меняет source identity квалификационного
модуля. Старые отчёты сохраняются как исторические; старый source-bound
checkpoint воспроизводится соответствующей исходной версией, а не получает
новую идентичность задним числом. Уравнения установки не изменены.


## Проверка поставки восстановления — 9 ноября 2026

Профильные проверки: 60 passed; полная локальная поставка: 456 passed,
восемь фаз, точная инвентаризация 1416 файлов и 788 ресурсов.
Отчёт: `artifacts/local-resume-delivery-v1/report.json`.
CLI также проверен из установленного wheel в свежем venv вне checkout
с изолированным Python: продолжение из промежуточной и конечной квитанций
побайтно воспроизводит журналы и checkpoint короткого 0,3-секундного профиля.
Отчёт: `artifacts/installed-resume-check-v1/report.json`.
Короткий профиль явно заменяет только горизонт/границы окон и проверку
установления тестовыми настройками. Это программная проверка restart,
а не допуск полного сценария load rejection или физическая валидация.
