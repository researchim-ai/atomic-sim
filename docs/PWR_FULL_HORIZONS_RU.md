# Локальные полные горизонты связанного reduced-PWR

> Ранние исторические результаты ниже получены до исправления коэффициента n21 IF97
> во внешнем benchmark 9 ноября 2026. Их source-bound приёмка автоматически
> не перенесена на новое ядро. Актуальные повторные проверки указаны в
> [текущем статусе](CURRENT_STATUS_RU.md) и
> [протоколе внешнего сравнения](EXTERNAL_BENCHMARK_RU.md).


Это длительный численный профиль исследовательской библиотеки, отдельный от
быстрой регрессии и проверки wheel. CI и внешние runners не используются.
Новые команды не сокращают длительности существующего протокола
`atomic_model_controlled_plant.qualification` и не меняют его критерии.

```bash
python -m scripts.verify_pwr_horizons
```

По умолчанию выполняются восемь полных случаев с последующим точным replay:

- `nominal`: 3600 с;
- `scram`: 60 с;
- `coastdown`: 1800 с;
- `load_rejection_equilibrium`: 7200 с;
- `feed_disturbance`: 120 с;
- `sink_disturbance`: 120 с;
- `natural`: 1800 с;
- `natural_perturbation`: 120 с.

Старый `load_rejection` на 600 с не входит в принимаемую матрицу:
его критерий полного установления ранее не прошёл. Более короткий случай
не переименовывается в успешный, а 7200 с остаётся отдельным протоколом.

Для выбранных случаев можно выполнить:

```bash
python -m scripts.verify_pwr_horizons --cases scram feed_disturbance --output artifacts/my-pwr-horizons
```

Такой результат имеет `complete_default_matrix=false`, даже если выбранные
случаи прошли. Полнота списка и успешность выбранного поднабора — разные поля.
Каждый запуск использует новый каталог; старые отчёты и failed cases сохраняются.
Можно продолжить работу на основе ранее завершённых случаев:

```bash
python -m scripts.verify_pwr_horizons --jobs 4 --reuse-from artifacts/previous-pwr --output artifacts/continued-pwr
```

`--jobs` ограничивает число независимых локальных случаев значениями 1–4;
по умолчанию worker один. У каждого численного процесса BLAS/OMP-параллелизм
ограничен одним потоком. Число workers не меняет модель, горизонты и допуски.
Приёмка и запись общего progress выполняются после завершения каждого случая.

`--reuse-from` не меняет прежний каталог. Случай повторно проверяется по native
отчёту, протоколу, текущей source identity, хешам trace/checkpoint и уже
завершённому replay. Только такая совокупность допускает reuse. Сам replay
для принятого старого случая не запускается заново: это явно записывается
в `reused_from` и политике итогового отчёта. Повреждённые свидетельства не
используются; причина сохраняется, и случай рассчитывается в новом каталоге.
Незавершённая траектория не продолжается с произвольной последней строки trace:
если нет полного принятого результата и replay, случай запускается заново.

`--phase-timeout-s` ограничивает wall time отдельного расчёта или replay
(по умолчанию 1800 с). Тайм-аут — отказ этой проверки, а не завершённый
физический горизонт. Неполный trace сохраняется в каталоге случая.

## Приёмка

Для каждого случая новый процесс выполняет прежний native runner.
Проверяются полный заявленный горизонт, отсутствие ошибки, точный протокол,
source identity, все обязательные checks и численные бюджеты ledger.
Сверяются SHA-256 trace и checkpoint; JSON-кортежи/списки сравниваются через
каноническую сериализацию, а не через несовместимое Python-равенство.

Для нового расчёта другой процесс восстанавливает checkpoint и воспроизводит
весь журнал команд. Код выхода, хеш checkpoint и число ревизий должны совпасть.
Только успешная совокупность расчёта, проверки отчёта и replay принимает случай.
Остальные случаи выполняются и после отказа предыдущего. `progress.json`
сохраняет завершённые записи; `report.json` имеет контрольную сумму содержимого.

Хеши исходной реализации и скрипта сверяются до/после. Эти контрольные суммы
не удостоверяют автора отчёта и не заменяют проверку происхождения измерений.
Верхнеуровневый `passed` требует успеха всех выбранных случаев и неизменности
контролируемой реализации. Для полного стандартного профиля дополнительно
требуется `complete_default_matrix=true`.

## Границы результата

Это модель `pwr-reduced-flow-controlled`, а не паспорт реальной установки.
Здесь проверяются существующие численные бюджеты и конкретные сценарии.
Длительность горизонта не доказывает применимость к произвольным возмущениям,
экспериментальную точность или работоспособность неподдержанных режимов.

Профиль не является сравнением временных шагов. Такие сравнения должны иметь
отдельные настройки и критерии; совпадение одного полного replay их не заменяет.
`validated=false` и `plant_referenced=false` сохраняются.
