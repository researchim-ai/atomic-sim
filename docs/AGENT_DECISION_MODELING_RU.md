# Моделёр как среда принятия решений для агента

Срез: 11 ноября 2026. Предыдущее [сравнение](MODELER_COMPARISON_RU.md)
не подтвердило общего лидерства. Перспективная специализация Atomic Sim —
готовая воспроизводимая среда для обучения и проверки решений, тесно
связанная с физическими балансами и областью применимости модели.

## В чём может быть преимущество

Обычный расчётный сценарий отвечает: «Что произойдёт при заданных входах?»
Агенту постоянно нужен другой рабочий процесс: «Какие из этих действий
можно сравнить из одного состояния, почему некоторые не подходят и можно ли
ещё применить выбранное решение?» Чтобы этим пользоваться, разработчику
не должно требоваться отдельно строить планировщик, хранение ветвей,
проверку происхождения и обработку отказов физики.

Это преимущество удобства и проверяемости конкретного продукта. Нельзя
утверждать, что других моделёров с такими отдельными механизмами нет:
[FMI 3.0](https://fmi-standard.org/docs/3.0.1/) уже описывает сохранение
состояния и многократные расчёты для MPC, а также направленные и сопряжённые
производные. [BOPTEST](https://ibpsa.github.io/project1-boptest/) предлагает
общий интерфейс управления и KPI. Поэтому «checkpoint», «API» или
«производные» по отдельности не объявляются уникальными изобретениями.

Наша проверяемая ставка — связка нескольких возможностей в библиотеке:

- сравнение действий из одного точного состояния без изменения живой модели;
- объяснимый результат каждой ветви: ошибка цели, затраты управления,
  балансы, превышенные лимиты или конкретный отказ расчёта;
- отдельные статусы нарушения пользовательского ограничения и выхода
  за допустимость уравнений;
- применение решения с проверкой происхождения и актуальности состояния;
- воспроизводимые траектории, пригодные для обучения предпочтениям,
  отладки политики и проверки модельного планирования.

## Что реализовано сейчас

Добавлен пакет `atomic_model_decision` для `HeatedHEMNetwork`.
`evaluate` независимо проигрывает ограниченный набор последовательностей
управления и возвращает запечатанный JSON-пакет. Живая сеть не продвигается.
Каждая ветвь начинается с одного checkpoint, включая историю управления,
источники и состояние стенки. Схемы Русанова, HLLC и локальный HLLC поддерживаются.

Результат ветви содержит наблюдения, checkpoint и метрики с единицами:
интеграл абсолютной ошибки температуры стенки K·с, абсолютную энергию
предписанных мощностей Дж, невязки массы кг и энергии Дж, энтропийный остаток Дж/К.
Статусы:

- `eligible` — расчёт завершён, балансы и наблюдаемые ограничения соблюдены;
- `constraint_violated` — превышен заданный температурный или давленческий лимит;
- `model_rejected` — вычисление отклонено моделью, причина и номер шага сохранены;
- `balance_rejected` — нарушен установленный допуск баланса.

Цель пока одна: температура выбранной стенки. Отбор лексикографический:
допустимые ветви, затем меньшая ошибка цели, меньшая абсолютная энергия
управления, затем id. Если подходящих ветвей нет, `selected_id=null`;
действие не подставляется автоматически. Список кандидатов не является
непрерывной оптимизацией: лучшая ветвь среди предложенных не обязательно
глобально оптимальна.

## Ограничения сравнения

Кандидаты имеют одинаковый горизонт и одинаковую сетку решений. Это не даёт
получить лучшую оценку просто за более короткую симуляцию или более редкое
измерение ошибки. Метрика использует прямоугольную квадратуру по правым
концам интервалов; её точность зависит от выбранной сетки.

Проверяются все начальные и последующие наблюдения. Температурные и
давленческие ограничения **не гарантируются между наблюдениями**. Контроль
допустимости самой физики продолжает работать на этапах интегратора.
Ни `eligible`, ни слово «ограничение» не означают подтверждение ядерной
безопасности, экспериментальной точности или вероятности безотказности.

Область — прежняя однофазная жидкость с линейной стенкой. Трение и кипение
этим API не разрешаются. Будущее неопределённо из-за ограниченности модели,
но статистическое распределение такой неопределённости здесь не вводилось.

## Как применяется решение

`commit` проверяет подпись источников и точное исходное состояние,
заново проигрывает **весь** набор кандидатов и сверяет полный пакет.
Подмена оценки, выбранного id, наблюдений или checkpoint, даже с
пересчитанным внешним digest, отклоняется при replay.

Перед изменением живой модели её checkpoint проверяется ещё раз под
транзакционной блокировкой. Если другое действие было выполнено во время
планирования, старое решение отклоняется; чужое изменение не откатывается.
Выбранная история применяется через штатный проверяемый restore.
Пакет предназначен для доверенного программного клиента: checksum
подтверждает целостность, а не криптографическую подлинность отправителя.

## Бюджеты

Не более 16 кандидатов, восемь интервалов на кандидата, 5 мс на ветвь,
20 мс суммарного прогнозного времени; входной JSON не более 64 КиБ,
выходной — 64 МиБ. Допустимые мощности проверяются основной моделью.
Расчёты пока последовательные и основаны на replay checkpoint.
Логические бюджеты не являются дедлайном реального времени: цена зависит
от числа внутренних шагов и длины исходной истории. Ускорение планировщика
и промышленный real-time контракт не заявляются.

## Пример

```python
from atomic_model_decision import evaluate, commit
from atomic_model_multiphysics.provenance import unseal
from scripts.verify_agent_decisions import setup

model, candidates, target, limits = setup('wall_control')
packet = evaluate(model, candidates, target=target, limits=limits)
report = unseal(packet)
if report['selected_id'] is not None:
    observation = commit(model, packet)
```

Полный запускаемый пример: [heated_decision.py](../examples/planning/heated_decision.py).
В примере сравниваются отключение нагрева, мощность 1 МВт и охлаждение
−100 кВт. Это тестовые входы ограниченного исследовательского стенда,
не рекомендации управления установкой.

## Проверка

Два случая на трёх схемах дают шесть путей. В обычном случае сильный нагрев
нарушает пользовательский предел. В случае стенки 899,999 К он вызывает
отказ этапа при выходе за верхнюю границу модели 900 К. Обе ситуации
отличаются от успешного расчёта, а живая модель при оценке не меняется.

Для каждого пути проверяются повтор с обратным порядком кандидатов,
совпадение применения с чистым последовательным расчётом и отказ повторного
применения устаревшего пакета. Unit-тесты дополнительно проверяют подмену
пакета, NaN, бюджеты, разные горизонты/сетки и изменение живого состояния
между планированием и применением.

```bash
python -m pytest -q tests/test_agent_decisions.py
python -m scripts.verify_agent_decisions --output artifacts/my-decisions
python examples/planning/heated_decision.py
```

[Машинный протокол и результаты](benchmarks/agent_decision_modeling_v21.json).
Физическое ядро не изменялось; предыдущие сравнения с независимой Modelica
не считаются новым внешним испытанием самого планировщика.

Поставка: **1171 тест прошёл**, все восемь фаз локальной проверки выполнены.
Один полный путь — оценка, перестановка кандидатов, replay-применение и отказ
устаревшего решения — точно повторён из свежего wheel вне checkout.
Полная матрица из wheel не повторялась. Подпись физического ядра сохранена.

## Следующие отличия, которые нужно доказать

1. **Планирование под неопределённостью:** сравнивать одно действие на общем
   ансамбле параметров и возмущений; отделять разброс модели от численной ошибки.
2. **Испытание агента на численных артефактах:** переносить фиксированную
   политику между шагами и сетками; обнаруживать выигрыш reward за счёт дискретизации.
3. **Сложные воспроизводимые задания:** длительные переходы, задержки и шум,
   отдельные сценарии обучения и оценки, одинаковые возмущения для политик.
4. **Доказуемая цена обучения:** throughput, p95 задержки, память и качество
   управления при одинаковом вычислительном бюджете с внешней средой.

Пока реализован и проверяется первый рабочий слой сравнения решений.
Остальные направления не отмечаются завершёнными и не используются
для заявления «у конкурентов такого нет».
