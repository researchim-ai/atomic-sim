# Паспорт станционной модели и перенос конфигураций

[English](STATION_CAPABILITIES_EN.md)

Пакет `atomic_model_station_capabilities` предоставляет паспорт `StationEnv` в JSON и средства сохранения, проверки и переноса настроек. Он входит в wheel и работает вне исходного репозитория.

## Как прочитать паспорт

```bash
python -m atomic_model_station_capabilities passport --output results/passport.json
```

В Python:

```python
from atomic_model_station_capabilities import passport

report = passport()
for item in report["qualifications"]:
    print(item["kind"], item["current_source_matches"], item["scope"])
```

В паспорте перечислены Python/JSONL/Gymnasium-интерфейсы, команды оператора, правила видимости наблюдений, настройки по умолчанию, реализованные области термодинамической диаграммы и модели теплоотдачи. Построение паспорта не запускает расчёт станции.

Доступность интерфейса, допустимость входных настроек и приёмка физического сценария — отдельные свойства. В частности, границы диаграммы EOS не являются подтверждённым рабочим диапазоном всей станции. Указанные ограничения и статусы относятся к станционной среде; другие исследовательские решатели репозитория имеют собственные области проверки.

## Какие доказательства включены

В wheel находится индекс двух опубликованных протоколов: [повторной приёмки часового номинала v105](STATION_NOMINAL_REQUALIFICATION_RU.md) и [пяти примеров API v106](STATION_EXAMPLES_RU.md). Для каждого сохранены контрольная сумма исходной квитанции и отпечаток её научных зависимостей. `current_source_matches` сравнивает этот отпечаток с текущей реализацией соответствующего протокола.

При несовпадении исходников запись сохраняется с ложным признаком совместимости. Из неё не создаётся подтверждение новой версии. Повреждённый индекс или неизвестная запись отклоняются. Если исходники меняются во время чтения паспорта, чтение также завершается отказом.

`current_source_matches` проверяет именно исходники. Он не подтверждает совпадение версий Python, NumPy/SciPy, аппаратуры или результатов нового исполнения. Для другой вычислительной среды по-прежнему нужен воспроизводимый запуск соответствующего протокола.

Индекс — опубликованная запись проекта с контрольными суммами. Он не является независимой экспертизой или цифровой подписью третьей стороны. Полные математические деревья не загружаются при запуске паспорта; их происхождение раскрыто в связанных протоколах. Приёмка номинала относится только к объявленному рецепту, а примеры API не квалифицируют физические сценарии.

`experimental_validation`, `industrial_plant_qualified` и `full_r1_accepted` остаются ложными. Полный выбег, обязательная матрица R1 и экспериментальная валидация сохраняются среди ограничений паспорта.

## Сохранение и проверка настроек

```bash
python -m atomic_model_station_capabilities export-config --output results/config.json
python -m atomic_model_station_capabilities validate results/config.json
```

Формат `station-env-config/v2` содержит полный набор полей `EnvConfig`, отпечаток исходников станционной модели и контрольную сумму содержимого. Проверка использует обычные валидаторы среды и отказов. Она не запускает симуляцию и не объявляет настройки физически квалифицированными.

Все поля должны быть заданы явно. Неизвестные параметры не отбрасываются, отсутствующие поля не получают неявных новых значений по умолчанию. Не поддерживаемые текущей версией названия корреляций и значения параметров отклоняются.

## Перенос существующего словаря EnvConfig

Для полного JSON-словаря, полученного через `dataclasses.asdict(config)`, используется явный входной формат `envconfig-raw/v1`:

```bash
python -m atomic_model_station_capabilities migrate old-config.json --from-format envconfig-raw/v1 --output results/config.json
```

В файл записывается новая конфигурация. В stdout выводится JSON-аудит: отпечаток входа, предыдущая и новая привязка к модели, список удалённых полей и признак необходимости повторной квалификации. Поля не удаляются, численные настройки не меняются. Если валидатор упорядочил список независимых отказов, это отмечается отдельно.

После изменения научных исходников старый документ v2 не проходит обычную загрузку. Для явного переноса тех же настроек на новую версию:

```bash
python -m atomic_model_station_capabilities migrate previous-config.json --from-format station-env-config/v2 --allow-rebind --output results/rebound-config.json
```

Такой перенос устанавливает `requalification_required=true`. Он подтверждает допустимость настроек в новой версии, но не повторяет её испытания и не переносит накопленную историю, состояние регуляторов или физический checkpoint. Checkpoint не принимается как файл конфигурации.

Все выходные файлы должны быть новыми; существующие результаты и пути через символические ссылки отклоняются. Входной JSON ограничен 1 МиБ. Исходный файл при переносе сохраняется.

## Использование из Python

```python
from dataclasses import asdict
from atomic_model_station_env import EnvConfig, StationEnv
from atomic_model_station_capabilities import migrate_config, load_config, RAW_FORMAT

original = EnvConfig(max_steps=3, tick_s=.02, automatic=False)
document, audit = migrate_config(asdict(original), from_format=RAW_FORMAT)
env = StationEnv(load_config(document))
observation, info = env.reset()
```

Повторная привязка конфигурации не является способом миграции старого checkpoint. Для воспроизведения рабочего состояния требуется соответствующая версия исходников и штатный механизм восстановления.

## Приёмка поставки v107

Прошли 60 целевых тестов, включая 20 новых. Установленный вне репозитория wheel повторил 20 новых тестов и все восемь JSON проверочного протокола целиком. Проверены CLI паспорта, экспорт, валидация, перенос полного словаря, отказ устаревшей конфигурации, запрет неявной перепривязки и явная перепривязка с признаком необходимости повторной квалификации. Реальные переходы среды и восстановленный checkpoint совпали с исходной конфигурацией точно.

Научный backend не изменён; оба включённых отпечатка опубликованных протоколов совпадают с текущими исходниками. Полный набор тестов библиотеки и длительные физические сценарии в этом этапе не перезапускались.

NPP-16.04 принят в области станционного паспорта, документированных форматов конфигураций и отчётности. Всего 50/76 задач плана, открыто 26; полная R1 остаётся открытой. [Машинный протокол](benchmarks/station_capabilities_v107.json).
