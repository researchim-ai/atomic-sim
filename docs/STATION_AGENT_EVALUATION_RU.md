# Разделения сценариев и полная оценка эпизодов агента — v87

Новый пакет `atomic_model_station_evaluation` работает поверх существующего
`StationEnv`, не вводя отдельной физики для обучения. Это реализация базовой
инфраструктуры NPP-14.04; полный промышленный набор задач NPP-14.03/04 ещё
не принят.

## Разделения без скрытого пересечения

`EvaluationCase` связывает конфигурацию среды с идентификаторами семейства
объекта, параметров, неисправностей и временного расписания. `validate_splits`
требует точного назначения всех случаев в непустые train/dev/test и проверяет
отсутствие пересечений по явно выбранным осям. По умолчанию проверяются все
четыре оси. Результат содержит канонический манифест и его хеш; перестановка
входных случаев не меняет манифест.

Дополнительно проверяется отпечаток сценария. Смена seed шума, численной
точности или максимального шага решателя не создаёт независимую физическую
задачу. Переименование неисправности также не позволяет обойти проверку.
Один такой сценарий не может находиться в разных выборках даже при разных
объявленных метках семейств.

Метки семейств задаёт автор эксперимента; валидатор не доказывает, что два
объекта представляют разные реальные установки. Поэтому манифест явно
содержит `unseen_physical_objects_validated=False`. Если в наборе одна
станция, разделение по объектам не объявляется: выбираются только реально
разделяемые оси и сохраняются в протоколе.

## Запуск политики и метрики

`evaluate` создаёт новую среду и новый экземпляр политики для каждого
эпизода. Фабрика политики не получает конфигурацию или идентификатор случая;
политика получает копии операторского наблюдения и публичной схемы действий.
Скрытые состояния и расписание неисправностей не передаются. Это разделение
API, а не изоляция произвольного Python-кода в песочнице.

Отчёт сохраняет каждый выбранный эпизод, включая ошибку при инициализации,
ошибку политики, недопустимое действие и отказ численной модели. В неуспешном
эпизоде остаются успешный префикс, число шагов, моделируемое время, накопленные
метрики и wall time. Неуспешные запуски не исчезают из общего знаменателя.

Отдельно записываются:

- интегралы нормированных ошибок мощности, давления и скорости по времени;
- длительность пригодных измерений каждого канала;
- интегральное время недоступности каналов;
- наблюдавшийся trip, причины termination/truncation;
- сумма существующего tracking reward;
- фактическое wall time и принятое моделируемое время;
- фаза, тип и код ошибки.

Средние ошибки делятся только на длительность пригодных измерений, а пропуски
сохраняются отдельно. Завершение вычисления **не считается успешным решением
производственной задачи**. Диагностическая точность, экономичность и качество
восстановления не выводятся из tracking reward.

`policy_id` — объявленная пользователем версия политики. Её подлинность не
проверяется автоматически; содержимое внешней модели или её checkpoint
следует версионировать отдельно. Исходники оценщика и физического backend
фиксируются в отчёте. Wall time является измерением и не должен участвовать
в побитовом сравнении научных результатов.

## Минимальный пример

```python
from atomic_model_station_evaluation import evaluate, hold_policy

# cases: список EvaluationCase; assignment: точное назначение имён в выборки.
report = evaluate(
    cases, assignment, lambda: hold_policy,
    split="test", axes=("parameter_family", "fault_family", "time_family"),
    policy_id="hold/v1",
)
```

`hold_policy` не посылает новых команд оператору; штатные контроллеры
действуют согласно конфигурации среды. Это воспроизводимая исходная
политика, не оптимальный промышленный регулятор.

## Локальная проверка

```bash
OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 MKL_NUM_THREADS=1 PYTHONPATH=src:. \
  .venv-layout/bin/python -m scripts.qualify_station_evaluation \
  --output artifacts/my-station-evaluation

OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 MKL_NUM_THREADS=1 PYTHONPATH=src:. \
  .venv-layout/bin/python -m pytest -q \
  tests/test_station_evaluation.py tests/test_station_env.py
```

Приёмочный пример содержит три коротких сценария одной исследовательской
станции и отрицательный контроль недопустимого действия. Он проверяет
проводку API и учёт запусков. Горизонты слишком коротки для вывода о качестве
управления, диагностики или восстановления; доставка неисправного измерения
не обязана завершиться внутри такого короткого эпизода.

Для полной приёмки NPP-14.04 остаётся наполнить эту инфраструктуру принятым
набором станционных задач, версионированными объектами и независимыми
параметрическими семействами. Нужны также метрики и исходные политики
NPP-14.03. Станционная приёмка остаётся 48/76; задачи не закрываются только
по наличию программного интерфейса.

## Результат v87

Прошли 49 целевых тестов, включая 18 новых. Три коротких станционных эпизода завершены; недопустимое действие сохранено как отдельный неуспешный запуск. Из установленного wheel вне проекта повторены 18 новых тестов и все три JSON-пакета приёмки; при сравнении исключены только wall_s и total_wall_s. Полного прогона библиотеки не было.
