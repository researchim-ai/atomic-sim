# Устанавливаемый EOS runtime, эксперименты и agent tools 1.1

Новый публичный пакет `atomic_model_runtime` входит в wheel/sdist Atomic Sim.
Он использует существующие уравнения EOS-сборки; отдельной копии физического
решателя в агентном интерфейсе нет. Поддержаны два независимых контура с
конечными торцевыми объёмами, теплоёмкие стенки и управление нагревом.
Модель остаётся экспериментальной синтетической однофазной сборкой.

```python
from atomic_model_runtime import create_eos_episode, create_eos_assembly

env = create_eos_episode({"preset": "mixed_ports", "episode_horizon_s": 0.1})
powers = [0.0] * len(env.config.action_channels)
observation, reward, terminated, truncated, info = env.step(powers)
```

`create_eos_assembly(spec, max_step_s=...)` также принимает полный
версионированный вход прежней сборки. Это ограниченная Python API, а не
произвольный редактор гидравлической топологии. `scripts` поставляется как
внутренний пакет драйверов; стабильные публичные точки входа расположены в
`atomic_model_runtime`. Не все остальные исследовательские scripts-backend
тем самым становятся поддержанными установленными моделями.

## Ресурсы и происхождение уравнений

Ранее драйверы требовали `validation/...` в текущем каталоге. Для публичного
пути бюджеты теперь читаются относительно установленного дистрибутива.
Рабочий каталог процесса не меняется. Ложный одноимённый бюджет в каталоге
пользователя не подменяет установленный ресурс. Каноническое имя ресурса
в provenance остаётся относительным; абсолютные пути машины не входят в
идентичность checkpoint.

Миграция затронула импорты/доступ к ресурсам, checksum helper и source closure.
У семи затронутых драйверов все классы уравнений и функции вне provenance/hash
сопоставлены AST с предыдущим замороженным архивом; они совпадают.
Численные бюджеты не ослаблены. Повторные кампании записываются отдельно
как `installed_*_campaign_v1.json`, прежние свидетельства не перезаписываются.

Исходники и обработчик ресурсов входят в новые подписи. Старый source-bound
checkpoint не автоматически совместим с изменённым runtime: для старых
артефактов сохраняется соответствующая замороженная поставка. Эта миграция
не является повышением физического статуса или заявлением калибровки воды.

## Эпизод EOS

Контракт `eos-agent-1.0.0` поддерживает пресеты `mixed_ports`, `uniform` и
`gravity`, фиксированный шаг действия и конечный горизонт. Конец интервала
вычисляется по номеру решения, чтобы не создавать лишний epsilon-шаг на 0.1 s.
Наблюдения — идеальные температуры всех тепловых портов, K; это не модель
реальных датчиков с шумом. Действие — полная именованная маска мощности, W,
диапазон каждой команды [-10000,10000]. Ни нормализации, ни скрытого clipping нет.

Reward равен нулю: эпизод предоставляет моделирование, а не неявно выбранную
задачу обучения. Цель/метрики агента должны задаваться явной внешней задачей.
`terminated` не используется, достижение горизонта даёт time_limit/truncated.
Численно отклонённый шаг оставляет последнее принятое состояние и возвращается
как `EpisodeRejected`; через tools — numerical_rejected, а не физическая
авария или успешное действие. Полная физическая диагностика доступна хосту
в native snapshot/manifest, без выдачи скрытого состояния в обычный tool-response.

Checkpoint сохраняет исходную рамку приращений и все журналы. Restore сверяет
конфигурацию, наблюдение, счётчики, времена и полные маски действий с native
квитанциями. JSON-restart и совпадение прямого API/agent route проверяются точно
в совместимой среде; универсального межплатформенного побитового обещания нет.

## Единый JSONL worker

`atomic-agent-tools` / `python -m atomic_agent_tools` сохраняют PWR-инструменты
и добавляют `create_eos_episode`. Версия протокола — 1.1.0.

```json
{"request_id":"r1","tool":"create_eos_episode","arguments":{"session_id":"thermal","config":{"preset":"mixed_ports","episode_horizon_s":0.1}}}
```

Далее используются те же inspect/step/save/restore/cancel/close. Для step
агент копирует revision и observation_id из текущего ответа и задаёт полную
маску heat-портов из `action_channels`. Дополнительный EOS backend не меняет
семантику PWR-действий: её диапазоны проверяются отдельно. Верхний default
observation_schema каталога относится к PWR; выбранная EOS-сессия возвращает
собственную схему наблюдений/действий и явный паспорт.

PWR и EOS могут сосуществовать в одном worker. Источник/контракт вложенного
checkpoint определяет backend при восстановлении; произвольный импорт Python
по имени модели/порта отсутствует. Оpaque checkpoint и host-only export/import,
монотонные ревизии, защита от старых наблюдений и синхронная отмена сохраняются.
Это всё ещё локальный JSONL, не MCP/JSON-RPC или распределённая система jobs.

## Эксперимент из файла

```bash
atomic-model-experiment examples/eos_thermal_experiment.json --output results/eos_full
atomic-model-experiment examples/eos_thermal_experiment.json --output results/eos_pause --max-decisions 1
atomic-model-experiment examples/eos_thermal_experiment.json --output results/eos_resume --checkpoint results/eos_pause/checkpoint.json
python -m examples.eos_agent_workflow
```

Эквивалент CLI: `python -m atomic_model_runtime.experiment ...`.
Вход schema1 содержит model_id, config и timeline. Событие timeline задаётся
**индексом решения** (начиная с 1), а не произвольным временем внутри шага:
`{"decision": 2, "heat_power_w": {...полная маска...}}`.
Все будущие события проверяются до создания выходного каталога/интегрирования.

Выход: normalized input, CSV и JSONL принятых состояний, checkpoint, manifest
с единицами, статусом, provenance и SHA-256 файлов. CSV содержит температуры
портов и общие энергетический/энтропийный residual; JSONL дополнительно
содержит массовые/импульсные residual отдельных контуров. Имена портов в CSV
обозначают температуры в K, а не мощности одноимённых действий.

При max-decisions статус paused; при численном отказе rejected и сохраняется
последний принятый prefix; completed не выдаётся за полный отвергнутый сценарий.
Checkpoint связан с нормализованным **всем** входом, включая будущий timeline,
и сверяет прошлые команды. Продолжение с другой будущей программой запрещено.
SHA не удостоверяет автора. Каталог результата создаётся эксклюзивно, без
перезаписи старого опыта. Ошибка программы не маскируется под модельный предел.

Артефакты публикуются при штатном завершении/паузе/численном отказе. Нет
фонового supervisor или гарантии checkpoint при принудительном убийстве процесса.
Физические calendar events, произвольный model registry, новые гидравлические
ветвления, двухфазность и целевой EOS этим релизом не закрываются.

## Приёмка интеграционного пути

Проверяются API ↔ tools ↔ файловый эксперимент, точный pause/resume,
подмена ресурсов через cwd, полный timeline до запуска, ограничения действий,
повреждённый checkpoint, старый PWR-контракт, JSONL subprocess вне project cwd,
независимые численные кампании и wheel вне checkout. Установленные импорты
контролируются по реальному пути, чтобы тест не использовал исходный checkout.
Зависимости научной среды унаследованы; это не герметичная поставка.

AI-11.07 может быть принят только в объявленном локальном JSONL scope;
FMI/co-simulation/удалённые агенты не реализованы и не заявлены. Остальные
AI-11 и физические пакеты продолжают иметь свои незакрытые критерии.
Материалы: `validation/ai11_public_eos_delivery_v1.json` и
`validation/ai11_public_eos_portable_replay_v1.json`.
